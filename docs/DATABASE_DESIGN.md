# طراحی دیتابیس MVP دلفین آبی

## تصمیم‌های تأییدشده

- مدل چندمستاجری: دیتابیس مشترک و ستون `organization_id`
- امنیت: RLS روی تمام جداول قابل دسترس از Data API
- ورود: حساب توسط ادمین، نام کاربری و رمز موقت
- پرداخت: فقط نقدی، کارت‌خوان یا انتقال بانکی در فاز اول
- درگاه بانکی و RFID واقعی: خارج از محدوده MVP

## ورود با نام کاربری

Supabase Auth ورود مستقیم با username ارائه نمی‌کند. راهکار MVP:

1. ادمین از یک عملیات سروری امن برای ایجاد کاربر استفاده می‌کند.
2. سرور یک ایمیل داخلی غیرقابل‌نمایش مانند `<uuid>@auth.dolphin.local` برای Auth می‌سازد.
3. username یکتا در جدول `profiles` به `auth.users.id` متصل می‌شود.
4. صفحه ورود ابتدا username را در یک endpoint سروری به هویت داخلی نگاشت می‌کند و سپس ورود رمز عبور انجام می‌شود.
5. رمز در هیچ جدول پروژه ذخیره یا قابل مشاهده نیست.
6. `must_change_password` کاربر را در اولین ورود به صفحه تغییر رمز هدایت می‌کند.

کلید secret/service-role فقط در سرور استفاده می‌شود و هرگز به مرورگر ارسال نمی‌شود.

ورود با username و تغییر رمز در Edge Function انجام می‌شود. مرورگر فقط publishable key را دریافت می‌کند. مجوز UPDATE مستقیم جدول profiles نیز در سطح ستون به full_name و phone محدود است؛ وضعیت حساب و الزام تغییر رمز فقط از مسیر سروری تغییر می‌کند.

ایجاد اولین سازمان و اولین مالک از مسیر bootstrap سروری انجام می‌شود؛ زیرا پیش از وجود مالک، سیاست RLS طبیعتاً اجازه ساخت نقش مالک را به کاربر عادی نمی‌دهد.

## قواعد مالی

- مبلغ با عدد صحیح و واحد ریال ذخیره می‌شود.
- پرداخت حذف نمی‌شود؛ فقط void یا refund می‌شود.
- کارمند دریافت‌کننده و زمان پرداخت اجباری است.
- تغییر وضعیت پرداخت فقط برای مدیر کل یا مدیر شعبه مجاز است.
- اتصال آینده به درگاه با افزودن provider و gateway transaction انجام می‌شود، بدون بازنویسی عضویت.

## کنترل ظرفیت

Constraint یکتای `(session_id, member_id)` از رزرو تکراری جلوگیری می‌کند. کنترل دقیق ظرفیت باید در یک تراکنش سروری اتمیک یا تابع رزرو انجام شود؛ شمارش ساده سمت مرورگر قابل اعتماد نیست.

## وضعیت این سند

فایل `database/schema.sql` در تاریخ ۱۴۰۵/۰۵/۱۸ روی پروژه Supabase با شناسه `slztfxrwrsnwyyrqfshc` اجرا و راستی‌آزمایی شد. ساختار فعلی هنوز به‌صورت migration رسمی در تاریخچه Supabase ثبت نشده است؛ پس از تثبیت bootstrap و جریان ایجاد اولین مدیر، migration تمیز از دیتابیس تولید می‌شود.
